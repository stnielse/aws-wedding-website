## Context

Session 9 (`2026-07-30-session-09-home-photos-and-manifest.md`) closed the
local Phase 2 tail: real engagement photos across the home page, the
`resize_engagement_photos` management command, and `ManifestStaticFilesStorage`
wired into `production.py` (still resolving against local disk). Test count sat
at 31 pass.

Session 9's handoff proposed a single-session Terraform lift covering S3, the
CloudFront distribution with two origins, DNS cutover, and phase 0 teardown.
Re-reading that plan against the original handoff's phase table exposed a
scope problem: **EC2 doesn't exist yet** (Phase 4 per the handoff), so a
CloudFront distribution with an "EC2 for everything else" origin has nothing
to point at, and flipping the Route 53 apex alias off phase 0 would take the
site down.

Session 10 accordingly scopes to the parts of Phase 3 that can land without
EC2 and without disturbing the live maintenance page. The user confirmed
this session that Phase 3 will span multiple sessions:

- **Session 10 (this session):** S3 media bucket + S3 static bucket + IAM
  policy scaffolding + `django-storages` + Option B staticfiles class
  (`S3StaticStorage` + `ManifestFilesMixin`) + LOGGING dict + surgical
  logger calls in app code. Local `collectstatic` and `Photo` admin upload
  verified against the real buckets. Site stays on phase 0.
- **Session 11 (planned):** VPC + subnets + security groups + RDS.
- **Session 12+ (planned):** CloudFront distribution (real one, with two
  origins), Route 53 cutover, phase 0 destroy. EC2 + gunicorn + nginx +
  GitHub Actions OIDC either fold into Session 12 or split to Session 13
  depending on how big that lands.

**Why Option B for staticfiles** (static also on S3+CloudFront, not just
media): Session 9's Manifest wiring produced ~110 hashed files, of which the
engagement JPEGs dominate the byte count. Serving those from nginx on a
t3.micro competes with gunicorn's request path; pushing them to S3 behind
CloudFront isolates the two and gets edge caching for free. The extra cost
is a second bucket + a custom storage subclass — cheap relative to the wins.

**Why the LOGGING work belongs here rather than later:** the handoff
amendment explicitly places the app-side `LOGGING` dict in Phase 2, which
means it's already overdue. Session 10 is opening `production.py` for the
storages change anyway; landing the LOGGING dict in the same edit is cheap.
Surgical logger calls (RSVP submit path, Photo save, exception handlers)
land alongside so the structured logging config actually has events to emit
before Session 12+ wires up the CloudWatch Agent.

Out of scope this session (deferred):

- **CloudFront distribution** — no EC2 origin yet, and standing up a
  static-only distribution would just be work we redo in Session 12.
- **Route 53 cutover** — apex + www stay pointed at the phase 0
  distribution. The site keeps serving the maintenance page.
- **`infra/phase0/` teardown** — the maintenance page is still the public
  face of the site; destroying it now leaves a DNS record pointing at a
  deleted distribution.
- **VPC / RDS / EC2** — Session 11+.
- **CloudWatch Agent + log groups + retention + ERROR alarm** — infra side
  of logging, needs EC2 to run the agent. Session 12+.
- **GitHub Actions OIDC deploy role** — no EC2 to deploy to.

## Decisions locked this session

*(Filled in during execution.)*

### Module directory naming

| Area | Decision |
|---|---|
| Path | `infra/phase3/`, matching the existing `infra/phase0/` convention. The original handoff sketched `infra/` at the top level (no phase suffix) as the "real" module, but a suffix keeps side-by-side operation clean while phase 0 is still live. Renaming to plain `infra/` happens when phase 0 is destroyed (Session 12+). |

### Two buckets, not one prefix

| Area | Decision |
|---|---|
| Layout | Separate `${project}-media` and `${project}-static` buckets rather than one bucket with `media/` + `static/` prefixes. |
| Why | Different lifecycle rules (media wants versioning + long retention; static is regenerated on every deploy). Different eventual CloudFront cache behaviors. Different IAM scope even though we currently grant both to the same role — separation lets us tighten the static grant to read-only from CloudFront's perspective later. |

### Option B — `S3StaticStorage` + `ManifestFilesMixin`

| Area | Decision |
|---|---|
| Static backend | Custom `ManifestS3StaticStorage(ManifestFilesMixin, S3StaticStorage)` in `config/storage_backends.py`. |
| MRO order | `ManifestFilesMixin` first so its `post_process` hashing runs before `S3StaticStorage.save`. |
| Why not `S3ManifestStaticStorage` from `django-storages` | Older versions shipped one; recent versions dropped it in favor of the DIY subclass since the mixin API is stable and the composition is one line. |

### LOGGING as stdlib JSON, not `python-json-logger`

| Area | Decision |
|---|---|
| Formatter | Hand-rolled `JsonFormatter` in `backend/config/log_formatters.py`, ~20 lines. |
| Why not `python-json-logger` | One less dependency to pin/audit for a trivial amount of code. Emits the same shape (timestamp, level, name, message, extra fields). |
| Fields | `timestamp` (UTC ISO8601), `level`, `logger`, `message`, plus any `extra` keys the caller passed. `exc_info` gets serialized to `exception.type` + `exception.message` + `exception.stack`. |

### No CloudFront this session

| Area | Decision |
|---|---|
| Distribution | Not created. |
| Why | (a) No EC2 origin exists yet, so we'd be creating a static-only distribution now and rebuilding it with two origins in Session 12. (b) The `AWS_S3_CUSTOM_DOMAIN` env vars stay optional; direct S3 URLs work for local verification. (c) Session 9's home-page images are still served from local Django (via `{% static %}` → local disk), not the new static bucket, until we deploy. |

### PII-free log records

| Area | Decision |
|---|---|
| RSVP submit log | `guest_id` only, no `name` or `email`. |
| Photo upload log | `photo_id` + `size_bytes`, no `caption`. |
| Why | Structured logs will ship to CloudWatch (Session 12+); CloudWatch retention is 30 days per handoff amendment, but IAM controls on log-group read differ from DB row read. Keeping PII out of logs preserves the DB as the single access-controlled surface for personal data. |
